React로 화면을 만들던 사람이, 지금은 그 화면이 어디서 깨지는지를 찾습니다. 만드는 일과 부수는 일은 결국 같은 질문을 방향만 바꿔 던집니다 — 이 구조에서 무엇이 먼저 무너지는가.

컴포넌트 상태와 API 응답을 직접 읽을 수 있으니, 재현 경로를 개발자가 바로 쓸 수 있는 언어로 적습니다. 그래서 테스트도 기능 목록 순서가 아니라 위험한 순서로 봅니다. 사람이 매번 똑같이 반복하는 확인은 스크립트와 AI 쪽으로 넘기고, 판단이 필요한 자리에 사람을 남겨둡니다.

> 나무처럼 꾸준히 가지를 뻗어, 결국 열매를 맺는 사람이 되고 싶습니다.

I used to build the screens. Now I find where they break — it turns out both jobs ask the same question from opposite sides: what gives way first in this structure?

Because I can read component state and API responses myself, I write reproduction steps in language a developer can act on directly, and I test in order of risk rather than in order of the feature list. Repetitive checks go to scripts and AI; people stay where judgment is actually needed.

</details>

## How I Work

회귀 검증 사이클을 `16시간 → 6시간` 으로 줄였습니다. 스위트를 병렬로 쪼개고, 매번 사람이 확인하던 구간을 자동점검으로 옮긴 결과입니다.

- **7단계 QC 프로세스 가이드** — 검수 절차를 팀이 같은 기준으로 판단할 수 있게 문서화
- **RBT(Risk-Based Testing) 분류 체계** — 기능 목록이 아니라 위험도 순으로 테스트 우선순위 결정
- **온보딩 문서** — 신규 입사자가 첫 배포 검수에 바로 투입될 수 있는 수준까지
